# Peptide Catalog Data

This directory contains the canonical peptide catalog used by Peptide Explorer.

## Current catalog

The current catalog was generated from the **IUPHAR/BPS Guide to PHARMACOLOGY (GtoPdb) 2026.2 release**, published 2026-06-15.

Current imported counts:

- **2,452 total peptide records**
- **837 endogenous peptide records**
- **1,615 other characterized peptide records**
- **141 records marked approved by GtoPdb**
- **3 records marked withdrawn**

The source export is:

`https://www.guidetopharmacology.org/DATA/peptides.csv`

The catalog should be described as a broad curated catalog of documented peptide ligands from the sources imported so far. It is not a mathematically exhaustive list of every peptide sequence that could exist.

## Files

### `peptides.jsonl`

The canonical catalog. Each non-empty line is one independent JSON object representing one GtoPdb ligand record.

JSON Lines is used because it is easy to stream, diff, validate, append, process with scripts, and migrate into a database later.

The current schema version is **2**.

Each record has a stable `record_id`, currently based on the GtoPdb ligand identifier, for example:

```json
{"record_id":"gtopdb:1234","canonical_name":"example peptide","primary_category":"endogenous peptide","evidence_level":"E0"}
```

`record_id` is the identity key. Human-readable peptide names are **not required to be globally unique** because distinct ligand records may legitimately share the same name.

Important fields include:

- `record_id`
- `canonical_name`
- `display_name`
- `aliases`
- `primary_category`
- `secondary_tags`
- `origin_or_species`
- `sequence`
- `sequence_length`
- `mechanism_or_targets`
- `biological_role`
- `studied_uses`
- `approved_indications`
- `evidence_level`
- `evidence_summary`
- `meaningful_human_evidence`
- `regulatory_status`
- `safety_summary`
- `identity_status`
- `database_ids`
- `peptide_details`
- `sources`
- `last_verified`

Unknown values remain `null` or empty collections. Import or enrichment tools must not invent missing values.

### `catalog_metadata.json`

Machine-readable metadata describing the catalog format, schema version, source release, record count, identity key, verification date, and import method.

### `catalog_summary.json`

A small generated summary intended to make the catalog easy to inspect without opening the large JSONL file. It contains total records, category counts, evidence-level counts, approval/withdrawal counts, source release, and identity information.

GitHub's web and mobile viewers may truncate large text files such as `peptides.jsonl`, so `catalog_summary.json` is the preferred way to confirm the current catalog size from the GitHub UI.

## Import process

The catalog is generated by:

```bash
python3 tools/import_gtopdb_peptides.py
```

The importer:

1. Downloads the current GtoPdb peptide CSV export.
2. Validates the response and expected CSV headers.
3. Parses the GtoPdb release metadata and peptide rows.
4. Assigns each ligand a stable `record_id` based on its GtoPdb ligand ID.
5. Preserves relevant source fields such as species, peptide type, sequence, approval status, PubChem identifiers, UniProt/Ensembl identifiers, INN, HELM, and modification information when present.
6. Converts the source rows into normalized JSONL records.
7. Writes `peptides.jsonl` and `catalog_metadata.json`.

The importer currently assigns conservative evidence levels:

- `E6` when GtoPdb explicitly marks the ligand as approved.
- `E0` for other imported identities until evidence is enriched from clinical, regulatory, or literature sources.

This is intentional: importing an identity does not imply that its therapeutic claims have been researched or validated.

## Validation and summary generation

Validate the catalog with:

```bash
python3 tools/validate_catalog.py data/peptides.jsonl
```

The validator checks JSON syntax, required fields, evidence-level values, and uniqueness of `record_id`.

Generate and verify the summary with:

```bash
python3 tools/summarize_catalog.py
```

The summary tool re-reads `peptides.jsonl`, counts the actual non-empty JSONL records, verifies that the physical record count matches `catalog_metadata.json`, and writes `catalog_summary.json`. A count mismatch is treated as an error.

## GitHub Actions workflow

The workflow `.github/workflows/import_gtopdb_peptides.yml` can be run manually from GitHub Actions and also runs for relevant pull-request changes.

Its pipeline is:

1. Check out the selected branch.
2. Download and import the current GtoPdb peptide catalog.
3. Validate the generated JSONL.
4. Verify the physical record count and generate `catalog_summary.json`.
5. Commit generated catalog files when they have changed.

This makes the GtoPdb import reproducible rather than relying on manually edited bulk data.

## Evidence levels

Peptide Explorer uses the following evidence scale:

- `E0`: identity only
- `E1`: biochemical / cell
- `E2`: preclinical
- `E3`: early human
- `E4`: controlled human
- `E5`: strong clinical
- `E6`: regulatory approval

Evidence applies to the specific molecular entity, not merely its family, target, or mechanism.

## Identity and future enrichment

The GtoPdb import is the initial catalog seed, not the final knowledge layer.

Future enrichment can add or improve:

- aliases and development codes
- biological roles and mechanisms
- targets and receptor families
- clinical-trial evidence
- approved indications
- safety information
- regulatory status from primary regulators
- PubMed and primary-literature citations
- additional authoritative peptide databases

True aliases may eventually be normalized across sources, but materially different peptide molecules, analogs, sequences, or chemical modifications should remain separate records.

The catalog is educational research data and is not treatment, dosing, reconstitution, injection, or sourcing guidance.
